## 2. What the last revision got right

Worth stating plainly, because these are the decisions that determine whether the product survives:

- **Attempt log as the single source of truth** (D-016). This is the correct call and it is rare. It makes multi-device merging a sort-and-replay instead of a conflict algorithm.
- **~2,000 verified questions in 3 sections instead of 10,000** (D-018). Quality over volume, and it matches real verification capacity.
- **Capacitor instead of TWA** (D-017). The stated reasons (Chrome dependency, thin-wrapper rejection) are exactly right.
- **Fix, re-grade and notify on a wrong key** (D-022). The correction path in `flow.md` F6 already handles the hard part.
- **`flow.md` with an explicit failure path per flow.** Most teams never write this, and it is already doing work — F6 is why P1-2 below is a *refinement* rather than a redesign.

## 3. Findings

Severity is about when it must be fixed, not how interesting it is.

### P1 — fix before any Step 2 code

**P1-1 · `core/` is not pure in the flow contract (→ D-030)**
`flow.md` states that `core/` never does I/O, then F2 shows `core/StreakTracker.ts › record()` marked `[DB write]` and F7 shows `core/Replayer.ts › rebuildAll()` writing cards and skills. Step 2 creates precisely these classes.
Impact: the purity rule is broken on the first day it matters, and the Elo/FSRS/replay logic — the only part that is worth unit-testing — becomes untestable without IndexedDB.
Fix: `StreakTracker.apply(attempt, todaySummary) → DailySummary`, `Replayer.rebuild(attempts, checkpoint) → { cards, skills }`, both pure; repositories do every write. Applied to `flow.md`.

**P1-2 · The 12-month retention rule contradicts D-016 (→ D-026)**
D-016 rebuilds FSRS and Elo by replaying the full log. §4 prunes raw attempts after 12 months. After pruning, replaying the remaining log produces *different* state than the original device — so a new device, or a correction re-grade (D-022), disagrees with the device that recorded the answers. Full-log replay also grows forever: ~2 MB of gzipped JSON per active student per year, i.e. ~2 GB at 1,000 users against 1 GB of free storage.
Fix: one compact checkpoint per user at each prune boundary; replay = checkpoint + attempts since. D-016 becomes "sync checkpoints only, never per-attempt state".

**P1-3 · The chosen log format cannot be appended to (→ D-027)**
D-023 already admits it: objects in Supabase storage have S3 semantics, so a monthly `.gz` must be **rewritten** every night for every active user — O(month × users) — and a failed run can corrupt a month. Attempts are also stored as JSON, where the UUID alone costs 36 bytes.
Fix: one immutable file per user per day, plus compact encoding (16-byte ID as base64url, pack index instead of question ID string, bitfield for mode). ~2–3× smaller, idempotent by construction, a failed run loses at most one day.

**P1-4 · `daily_stats` has two sources of truth (→ D-028)**
The sync payload carries client-computed `daily` aggregates, and the nightly job also derives stats from the same attempts. The client number is trivially inflated by a modified APK — and streaks are read from `daily_stats`, so it also matters as anti-cheat.
Fix: payload carries attempts only; the server computes the IST day from `at` within a 30-day window, else clamps to `receivedAt`.

### P2 — decide before the week they block

**P2-1 · Live mocks cannot be synchronised in v1 (→ D-029)**
A leaderboard only means something if students sit the same mock. D-024 deliberately ships no push, so a mock cannot be announced. F8 also held mock questions in memory only, so a phone call or a 4G drop ends the session — on the exact device class this app targets.
Fix: 72-hour window (Fri–Sun IST), server-registered start inside the window, session persisted locally with a TTL and resumable, ranking by score → time → submitted-at. No FCM, same anti-cheat properties. Add a larger question pool than 25 so students do not get identical sets.

**P2-2 · Content has zero slack, and Hindi is the hidden cost**
2,000 ÷ 35/day = 57 days inside Weeks 3–11 (63 days), while also building full-time. A verified bilingual MCQ with a source check is realistically 4–6 minutes, i.e. 2–4 hours every day. And `hi: null` is legal in the contract while the product promises Hindi from day one — a machine-translated Hindi *explanation* on a wrong English key is the worst-case trust failure for this app.
Fix: start verification in **Week 1**, not Week 3. Weight the 2,000 towards **real PYQs** (official answer keys, low risk, highest perceived credibility) — roughly 1,200 PYQ + 800 AI drafts. Make `hi` required to publish, with a separate "Hindi checked" flag in the admin queue. Two passes, not three. If pace slips, ship 1,200 questions in two sections — do not slip the date.

**P2-3 · Delete account is promised, has no flow, and would leave data behind**
Required by the DPDP Act and promised in the feature list. Deleting the Supabase auth user does not delete `attempt_inbox`, `daily_stats`, `question_reports`, or the log files under `users/<id>/`.
Fix: `delete_user()` cascade in the listed order, local wipe only after server confirmation. Added as F12.

**P2-4 · `eloSeed` never refreshes, so difficulty never self-calibrates on-device**
`question_stats.elo` updates nightly, but the phone only sees `eloSeed` from packs. D-005's promise requires a re-publish loop that exists in no roadmap row and no flow.
Fix: weekly repack of `eloSeed` (and only that field) for the next release; note it in the roadmap.

**P2-5 · Budget fiction to correct before it is spent**
Drafting 2,000 bilingual questions on a large model with three passes is ~₹4,500+, not ₹3,500. The line works only with a small model for drafts and the Batch API. And ₹1,500 contingency does not buy a Redmi 9A class phone — if one is not owned, the 50 ms target cannot be verified at all. Both noted in `PROJECT_SPEC.md` §12.

**P2-6 · Play Console logistics**
The 12-tester / 14-day rule applies to the **closed** track; the **internal** track has no such requirement and allows up to 100 testers. Recruit 20 to survive attrition, start the internal track in Week 4, and open the closed track once practice mode is usable — not in Week 11.
Also: Google blocks OAuth inside a WebView (`disallowed_useragent`). Sign-in must go through `@capacitor/browser` with a deep-link callback, and Supabase must allow both `https://…` and `capacitor://localhost` as redirect URLs. No flow mentions this, and it fails only on a real device.

### P3 — hygiene, cheap to fix, compounds if ignored

- `flow.md` folder map omitted `PracticeSession.ts`, `CardRepository`, `SkillRepository`, `DailyRepository` — all referenced by the flows. Now enumerated.
- No flow existed for "Report error" despite it being a promised feature with a server table. Added as F11, with one contract addition: `reports[]` in the sync batch (max 20).
- A correction can be half-applied: if the correction row arrives before the corrected pack, new attempts on that question still grade against the old key. Rule needed: the local `corrections` row overrides the key for **grading** immediately; the **display** updates when the pack lands.
- Do not block the tap on the transaction commit. To actually hit <50 ms on eMMC, render optimistically and flush on `onPause`. The old "250 ms vs 50 ms" figure argued the right design from a number that is probably pessimistic by ~5×.
- Fonts and Sentry together consume most of the 300 KB code budget. Consider letting Android's built-in Noto Devanagari render body text and self-hosting only headings; configure Sentry with `sendDefaultPii: false`.
- D-009 still cites "~10,000 concurrent at evening peak" — stale from the 8-week version.
- D-008 puts its supersede reason in the **Revisit when** field, which the template reserves for a trigger.
